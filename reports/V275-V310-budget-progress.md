# 全新请求的 600 秒预算迭代（2026-10-19）

本轮按用户要求把十亿条**全新配对请求**的单线程本机 CPU 外推不超过 600 秒设为硬约束，包含一次初始化、解析和 CSV 输出。使用此前固定的两批各 300 万条新请求：600 万对互不重复，并排除已知 development / validation 请求对。不开中间算子缓存和最终预测缓存。完整验证固定为 150053 条；只用 development 标签拟合，不读 holdout。

本机测量不保证另一台机器或另一种隐藏请求分布的速度。验证分是比赛误差评分，不能直接当成逐条完全正确的百分比。反复使用 validation 选择方案，也不能把它称为独立未知集分数。

## 已确认的新可行基线

V306：验证 **99.1137582293**；两批外推 **487.513363 / 489.678665 秒**，平均 **488.596014 秒 / 8.143267 分钟**；约 **0.46544 微秒/条**（查询部分）。峰值 RSS **1,711,685,632 bytes**。完整提交目录 **99,954,766 bytes**，压缩包 **99,035,255 bytes**。同一冻结程序完成全部测量，输入输出 pin 顺序逐行核对，资产 SHA 前后一致，每轮观测到一个运行线程。

700705 条 development 和完整 validation 逐条与独立 Python 模型预测一致。源码独立重编译得到的 Mach-O 全部文件支持节、甚至整个可执行文件 SHA 都与实测程序相同。证据：`V306-budget-profile.json`、`V306-budget-submission.json`；包为 `out/submission/final-v306/`。

对比：V254 验证 **99.5061105063**，全新请求平均 **1262.8925 秒 / 21.0482 分钟**；V274 验证 **99.6344970607**、**3353.8078 秒 / 55.8968 分钟**。这两个高精度配置不满足本轮的十分钟约束，仍保留。不能将它们的分数与 V306 的时间拼接，也未达到“99.5 分 + 新请求 600 秒”的更高联合目标。

## 结构改变

1. 从 V158 的紧凑周期 min-plus 响应恢复轻量分支。首轮旧程序的 300 万新请求 CPU 为 24.2423 秒，初始化 22.7283 秒，外推约 **527.3950 秒**；此前完整验证为 **99.0256649430**。这次重新测量采用新配对输入，没有借用旧重复请求的速度。
2. 对固定布局直接求值：已知单终端提示、相位连续存储、有限四锚点插值与饱和斜率，减少每次查询重复检查研究模式和空布局。普通路径和跨墙走廊均有固定路径；真实首跳、Line 费用、旧走廊共享规则、整数截断与并列选择保持原语义。这个估计仍是近似算法，不是物理最短路证明。
3. 修正模型只读 **56 个廉价特征**：原始几何、基准值、端口类别/lane、Net 方向和调整后位移。它不再读取原高精度方案的大型所选路径响应/phi 特征。代价是准确性低于 V254；速度余量换来 8 棵小树的部署空间。
4. 单树结果对安全范围内的叶值预先整数化；接近半整数的叶保留依赖基准奇偶的 IEEE 舍入。多树先从零累加残差，最后一次加基准，与训练端一致。V301 的严格逐行核对发现极少数半整数相差 1ps，拒绝该候选；修复后 V305 development 全部 700705 条一致，V306 完整 validation 亦全部一致。
5. CSV 去空白直接处理端点；连续的 From,To 片段一次复制。编译画像只由 development 输入生成，不供应标签。

固定布局求值与编译画像属于工程专门化，不宣称是新的最短路理论。小型残差学习借鉴 LightGBM；min-plus、周期响应、有限理想图和走廊分解属于已有方法。本题的组合实现和精度/存储/时间的实测选择才是这里的改进。既有参考文献、下载与阅读范围见 `papers/README.md` 和历史报告；本轮没有新增论文，也没有声称复现某篇论文的正式基准。

## 复现与提升门槛

研究构建：`scripts/prepare_budget_runtime.py`；完整验证与新请求测量：`scripts/benchmark_budget_runtime.py`；冻结：`scripts/freeze_budget_submission.py`。冻结脚本拒绝任何一批超过 600 秒、RSS 超 2GB、独立预测不一致、重建机器码不一致或完整目录超过 100MB 的候选。

## 余量内继续加大模型后的结果

V309 的 16 树修正器完整原生验证 **99.1170273590**；两批十亿外推 **551.963103 / 580.441155 秒**，平均 **566.202129 秒 / 9.436702 分钟**，每批均低于 600 秒。峰值 RSS **1,711,751,168 bytes**；完整包 **99,859,283 bytes**；归档 **99,134,183 bytes**。生成树头和 LLVM 画像无损压缩保存，重建时由 Python 标准库展开，最终重编译可执行文件 SHA 与实测文件完全相同。证据：`V309-budget-profile.json`、`V309-budget-submission.json`。

16 树仅比 8 树提高约 0.00327 分，查询代价明显增加。按此前用户的综合技术分优先选择，在本机验证分/CPU代入、假设一致性100时，V306 约 **95.2194**，V309 约 **94.5753**；V254 约 **89.0808**。这些均非官方技术成绩。默认构建 V306，V309 作为十分钟内更高验证分选项；600 秒筛选脚本同时输出精度优先和综合估分优先的结果，不将超预算候选列为可选。

V307 的模型前缀比较也已记录：最多 12 棵树的最好离线分为 99.1155758，仍未超过 V309。64 树最佳离线 99.12119，只改善约 0.00416；未作为完整原生达标配置。32 树的 V310 只生成 development 编译画像，没有将画像程序的时间称为提交版十亿吞吐。

下一步只在余量内比较更强修正器；没有完整通过这几项约束的候选不会取代已冻结版本。更高精度的下一条研究线应补充便宜的物理边界信号；当前纯几何/端口特征扩大到 64 棵树的收益已经很小。
